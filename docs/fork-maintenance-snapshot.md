## Причина ожидания около 28 секунд

Изолированный смешанный транспортный сценарий ждал, пока общий `Sessions` вернётся к одной управляющей сессии. Но этот счётчик включает логические сессии, сохранённые для переподключения, даже когда сокет уже закрыт.

Путь в текущем коде:

- [`SessionRegistry.Remove`](../internal/daemon/session.go#L493) удаляет привязку `byConn` и устанавливает `Conn=nil`, но сохраняет логическую сессию, MCP state и replay-cache.
- [`serveMCPConnectionWithHooks`](../internal/daemon/mcp_request_lifetime.go#L293) при выходе отменяет контекст соединения и запросы, затем ждёт завершения обработчиков.
- [`Server.handle`](../internal/daemon/server.go#L479) закрывает сокет, удаляет его из `conns` и вызывает `Remove`.
- [`SessionRegistry.Count`](../internal/daemon/session.go#L527) возвращает `len(r.sessions)`, включая сохранённые записи без сокета.
- [`deadPeerSweepInterval`](../internal/daemon/server.go#L402) равен `30 * time.Second`.
- [`Server.runMaintenance`](../internal/daemon/server.go#L409) по этому таймеру вызывает `SweepDead`, затем `SessionEnded`.
- [`SessionRegistry.SweepDead`](../internal/daemon/session.go#L540) окончательно удаляет записи, если процесс proxy уже завершился.

Ожидание примерно 27,8 секунды соответствует следующему проходу этого сборщика. Это не доказательство задержки закрытия сокета или утечки работающих обработчиков. Обработчик, игнорирующий отмену контекста, всё ещё способен задержать `requests.Wait`; такого случая в данном прогоне не доказано.

Исходные запросы MCP длительностью около 59 секунд остаются отдельным неразрешённым вопросом. Связь с хранением логической сессии не установлена.

Следующее возможное улучшение: отдельно показывать живые сокеты, сохранённые логические записи и transport-managed сессии. `RegisterDetached` используется активным HTTP transport без `net.Conn`, поэтому `Conn=nil` само по себе не означает отключение. Нельзя сокращать reconnect lifetime или ослаблять проверку освобождения реальных ресурсов только ради быстрого теста.

Артефакты подтверждённого смешанного прогона: `/tmp/gortex-agent-mixed-final.Qy9Y4v/gx767-2997214095/mixed-transport.json`. В нём 512 файлов, 50 757 узлов, 231 619 рёбер, 336 операций и 0 ошибок. В фазах с 1, 4 и 8 клиентами время ожидания очистки составило 27,74–27,83 секунды. После очистки оставалась одна управляющая сессия. Временные артефакты могут быть удалены системой.

## Что нужно сделать для установки и обновления из форка

Пользователь хочет:

1. Однозначно видеть, что запускается его сборка `kordax/gortex`, а не upstream. Идентификация должна показывать fork, версию, commit, признак dirty и источник обновления.
2. Устанавливать бинарник так, чтобы команда `gortex` была доступна из любой директории, с заменой используемого исполняемого файла и понятным откатом.
3. Активировать новую сборку в существующем управляемом демоне, сохранив его конфигурацию и хранилище.
4. Получать `gortex update` / `upgrade` и бинарные релизы из `https://github.com/kordax/gortex`, не возвращаясь незаметно к upstream.

Уже существует [`scripts/install-local.sh`](../scripts/install-local.sh): собирает текущий checkout с незакоммиченными исходниками, атомарно заменяет `~/.local/bin/gortex`, сохраняет `gortex.previous`, поддерживает `GORTEX_INSTALL_DIR`, dry-run и rollback. Этот скрипт сам не перезапускает демон и не меняет конфигурацию. Он проверен на временных назначениях; установка на реальную машину в этом этапе не выполнялась.

Реализовано в подготовке v1.0.0:

- [`cmd/gortex/upgrade.go`](../cmd/gortex/upgrade.go) использует `kordax/gortex`, закреплённый тег установщика и полное скачивание до исполнения. Автоматические upstream package-manager/go-install пути отклоняются.
- [`cmd/gortex/version.go`](../cmd/gortex/version.go) показывает `fork by kordax`, fork URL, SemVer и commit с честным dirty-признаком.
- Release workflow и установщик используют fork assets. Проверены offline-контракты, ShellCheck, actionlint и GoReleaser config. По отдельному решению пользователя GitHub CI перед первым выпуском не ожидается: конкретные платформы и отсутствие подписей ручного выпуска указаны в [fork-release.md](fork-release.md).
- Перед заменой работающего экземпляра нужно проверить путь команды в PATH, путь бинарника сервиса, владельца демона и фактическую версию после запуска. Не создавать второй демон и не менять ресурсные лимиты без отдельной необходимости.

## Историческая проблема SQLite

Ниже факты из сообщения пользователя об обслуживании 15 октября 2026 года. Рабочую БД для перепроверки этих фактов в этом этапе не открывали.

В `analysis_generations` накопилось 168 устаревших поколений. В журнале повторялись:

```text
mcp analysis generation prune failed
generation 179 nodes context deadline exceeded
```

Таймаут очистки составлял около 30 секунд.

При `EXPLAIN QUERY PLAN` удаления из `analysis_nodes` с `foreign_keys=ON` проверка внешнего ключа выполняла:

```text
SCAN analysis_process_steps USING COVERING INDEX analysis_process_steps_by_node
```

Индекс `analysis_process_steps_by_node` имел столбцы `(generation_id, node_rowid, process_id)`. Внешний ключ ссылался на `analysis_nodes(id)` через `node_rowid`, без `generation_id`. Поэтому у индекса не было нужного ведущего столбца для этого предиката.

При согласованном ручном обслуживании добавили три неуникальных индекса:

```sql
CREATE INDEX maintenance_analysis_steps_node_rowid
    ON analysis_process_steps(node_rowid);
CREATE INDEX maintenance_ref_view_builds_ref_view_id
    ON ref_view_builds(ref_view_id);
CREATE INDEX maintenance_dedicated_graphs_family_id
    ON dedicated_graphs(family_id);
```

После этого все 26 проверенных FK-предикатов использовали `SEARCH`, а не `SCAN`. Четыре других предполагаемых пробела оказались ложными: существующие частичные индексы с `WHERE ... IS NOT NULL` уже покрывали обращения. Не создавать их дубликаты.

Удалили 166 из 168 старых поколений, оставив два последних. Удалилось 52 706 764 строки `analysis_nodes` и связанные данные. `VACUUM` уменьшил БД с 67,2 до 7,19 GiB. Это историческое обслуживание, а не действия текущего этапа.

Реализация v22 добавляет эти три индекса в свежую схему и явную аддитивную миграцию без rebuild. Проверки на временных БД покрывают все 26 FK-предикатов, реальные DELETE/GC, целостность, upgrade v21, отдельную миграцию без reconciliation и повторное применение. Исторические maintenance-индексы не дублируются; существующие подходящие partial-индексы также не получают новых дублей. Произвольные эквивалентные индексы с другими именами миграция не распознаёт. Сохранён сравнительный benchmark, без нестабильного CI-порога времени. Подробнее: [sqlite-validation.md](sqlite-validation.md).

## Завершённый этап: раздельный учёт сессий

В `StatusResponse` и `ProbeResponse` добавлены `socket_sessions`, `retained_sessions`, `transport_sessions` и `session_counts_known`. Старый `sessions` сохраняет прежний смысл общего числа записей. Отсутствие known-флага у старого демона означает недоступные данные, а не ноль соединений. Строки `MCPSessionStatus` получили `connection_state`: `socket`, `retained`, `transport`. CLI показывает раздельные числа, состояние и возраст записи. Fallback probe в hooks сохраняет эти сведения.

Счётчики и строки собираются под одной блокировкой реестра, поэтому detach/rebind не могут дать противоречивую таблицу. Политика reconnect, replay-cache и 30-секундный сборщик не изменены. Детерминированные тесты проверяют сохранение состояния/replay после rebind, отсутствие ложного detach при поздней очистке старого сокета, атомарный snapshot при конкурентном detach, корректную классификацию HTTP и отмену выполняющегося запроса при закрытии реального `net.Pipe`.

Оба изолированных стенда теперь используют одно постоянное управляющее соединение и ждут освобождения сокетов. Оставшиеся логические записи сохраняются в runtime-отчёте. На прежнем размере смешанной нагрузки (512 файлов, 50 757 узлов, 231 619 рёбер, 336 операций) прошло 0 ошибок. Ожидание освобождения соединений составило 42,8–61,5 мс вместо прежнего ожидания логической очистки около 28 секунд. После фаз оставался один управляющий сокет и 3, 8, 17 retained-записей соответственно. Это исправление наблюдения и ожидания стенда, а не изменение срока хранения reconnect-записей.

Проверено на финальном коде:

- Полные race-наборы `internal/daemon` (13,740 с), `internal/hooks` (3,429 с), `cmd/gortex` (65,154 с).
- Новые daemon-регрессии: 20 повторов под race, 1,221 с.
- Смешанный транспортный сценарий с обычной сборкой: 17,449 с, 336 операций, 0 ошибок.
- Транспортный сценарий под race: 4 клиента, 100 чтений, batch/ledger, ошибки протокола, reconnect, worktree и конфликтующие edits; прошёл за 58,923 с.
- golangci-lint 2.15.0: 0 issues. Trivy HIGH/CRITICAL с `--ignore-unfixed` и secret scanner: без находок.

В первом CLI-прогоне был конфликт имени нового status-reader с переменной ledger-ответа; он исправлен, повторные полные CLI-проверки и lint прошли. Логи и профили: `/tmp/gortex-session-accounting.6Xj5lH`, mixed fixture `mixed/gx767-4241928611`, race fixture `transport/gx767-242151241`. Полный репозиторный race-набор для этого изменения не запускался; запускались указанные затронутые пакеты. Причина отдельных 59-секундных MCP-запросов остаётся неустановленной.
