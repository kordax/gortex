# Проверка SQLite

Схема v22 добавляет три индекса для проверок внешних ключей при удалении родительских строк:

| Дочерняя таблица | Ведущий столбец нового индекса | Почему прежнего индекса недостаточно |
| --- | --- | --- |
| `analysis_process_steps` | `node_rowid` | В прежнем составном индексе первым был `generation_id` |
| `ref_view_builds` | `ref_view_id` | Частичный индекс содержит только `state = 'building'` |
| `dedicated_graphs` | `family_id` | Частичный индекс содержит только `is_primary_base = 1` |

Имена `maintenance_*` совпадают с индексами, установленными при ручном обслуживании 15 октября 2026 года. Такая БД обновляется без их дублирования. Миграция аддитивна: граф не удаляется и переиндексация для изменения индексов не требуется. Как и при других переходах схемы, старый активный снимок анализа инвалидируется. На большой БД первое создание индексов может занять заметное время и место. `VACUUM` автоматически не запускается. Произвольные эквивалентные индексы под другими именами миграция не распознаёт.

## Что проверяется постоянно

`schema_foreign_key_indexes_test.go` входит в обычный `go test`. Все БД создаются в `t.TempDir()`.

- Перечисление объявленных FK через `pragma_foreign_key_list` и проверка индексного поиска для каждого дочернего предиката, включая составные ключи. Подходящие частичные индексы `WHERE ... IS NOT NULL` учитываются без дубликатов.
- Планы настоящих `DELETE` с включённым `foreign_keys`, в том числе точного удаления узлов из сборщика поколений.
- Новая БД, обновление v21 и обновление БД с историческими индексами: данные сохраняются, добавляются ровно три недостающих индекса.
- Явная миграция без предварительного применения свежей DDL и повтор той же миграции.
- Запрет удаления используемого узла и семейства, каскадное удаление завершённой сборки, очистка старых поколений с сохранением активного.
- `PRAGMA foreign_key_check` и `PRAGMA integrity_check` после операций.

Тест не привязан к имени выбранного индекса или полному тексту плана. Он проверяет `SEARCH` вместо `SCAN` для дочернего FK-поиска. Это требование к данному пути доступа, а не запрет всех сканирований в приложении: массовое чтение может обоснованно выбирать сканирование.

```bash
GOTOOLCHAIN=go1.27.3 go test -race -count=1 -timeout=5m \
  ./internal/graph/store_sqlite -run '^TestForeignKeyChildIndexes'

GOTOOLCHAIN=go1.27.3 go test -race -timeout=25m \
  ./internal/graph/store_sqlite
```

Полный пакет дополнительно проверяет транзакции, поколения, FTS, конкурентные подключения, отмену и остальные операции хранилища. Конечный набор тестов не доказывает корректность любой будущей схемы или любого объёма данных. При добавлении операции нужны проверки её инвариантов, отката, маршрутизации поколений и подходящего плана на характерных данных.

## Повторяемая диагностика скорости

Benchmark сравнивает свежую схему с историческим отсутствием индекса `node_rowid`. Он создаёт три поколения в отдельных временных БД и удаляет одно, оставляя два. Подготовка данных и проверка результата исключены из `ns/op`; жёсткого порога времени нет.

```bash
GOTOOLCHAIN=go1.27.3 go test -run '^$' \
  -bench '^BenchmarkForeignKeyGenerationPrune$' -benchtime=1x -benchmem \
  ./internal/graph/store_sqlite
```

Один диагностический запуск на машине разработчика для 1 000 узлов на поколение дал около 632 мс без индекса и 5 мс с индексом. Это иллюстрация конкретного FK-сканирования, не производственный SLO. Для сравнения изменений повторяйте замеры на одной машине и сохраняйте размер фикстуры, параметры запуска и результаты.

Если плана недостаточно для объяснения задержки, снимайте профиль только изолированного процесса:

```bash
artifacts=$(mktemp -d)
GOTOOLCHAIN=go1.27.3 go test -run '^$' \
  -bench '^BenchmarkForeignKeyGenerationPrune/steps=1000/indexed=true$' \
  -benchtime=1x -cpuprofile="$artifacts/cpu.out" -memprofile="$artifacts/heap.out" \
  -o "$artifacts/store_sqlite.test" ./internal/graph/store_sqlite
GOTOOLCHAIN=go1.27.3 go tool pprof -top "$artifacts/cpu.out"
```

Профиль всего процесса включает подготовку БД, даже если benchmark-таймер остановлен. Для длительных ожиданий дополнительно нужны block/mutex-профили и отмена контекста, а для транспортных задержек используется отдельный [агентский стенд](../bench/agent-transport/README.md). Установленная причина SQLite-очистки не доказывает причину прежних 59-секундных MCP-вызовов.
