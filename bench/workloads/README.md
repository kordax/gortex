# Fixed synthetic workloads

These Go benchmarks generate deterministic Go source in temporary directories and use the real indexer and SQLite store. They never start a daemon, read tracked repositories, call an LLM, or fetch an embedding model. Each test or benchmark installs a private test environment before constructing the indexer.

```sh
GOTOOLCHAIN=go1.27.3 go test -race ./bench/workloads
GOTOOLCHAIN=go1.27.3 go test ./bench/workloads -run '^$' \
  -bench . -benchmem -benchtime=1s -count=5 -cpu=4 > before.txt
# Apply a candidate optimization, then repeat into after.txt.
# Compare the samples with benchstat, including its confidence intervals.
```

The stable cases are:

| Benchmark | Timed work |
| --- | --- |
| `BenchmarkColdIndex/files=32` and `files=128` | One full index into a fresh SQLite store, including parsing, reference resolution and persistence |
| `BenchmarkWarmSearch/files=32` and `files=128` | Sequential exact-symbol queries cycling through the indexed function names |
| `BenchmarkParallelSearch/files=32` and `files=128` | Concurrent exact-symbol queries, with concurrency controlled by `-cpu` |

Each fixture contains eight uniquely named functions per file, with seven calls between functions in each file. The 32-file and 128-file cases therefore contain 256 and 1,024 functions. Generated source and names are deterministic, and a normal test compares the generated bytes across independent fixtures.

Cold indexing excludes source generation, parser registration, opening SQLite, schema initialization, indexer construction, validation and closing the store. It is a fresh application index, not a cold OS page cache or a daemon startup measurement. The source files may be in the OS page cache. `files/op`, `functions/op` and source-byte throughput describe one indexing operation; they do not count arbitrary graph nodes as source symbols.

Warm searches exclude fixture creation and indexing. Before timing, every expected function is checked against the real search backend, and the graph's function count must match exactly. Each timed query also verifies that its expected exact symbol remains in the result. This validation overhead is included in the reported query cost. Search itself can return related fallback hits, so an absent-symbol check rejects an invented exact match rather than requiring an empty result set. These are ranked search queries, not a claim that the backend implements case-sensitive filtering.

The parser registry is shared across iterations within each benchmark. The SQLite database is newly created for every cold-index iteration and shared by the readers in each warm-search case. Timing runs should use the same Go toolchain, `-cpu`, fixture size, machine and build settings. Avoid `-race` for performance comparisons; use it separately for correctness. Do not compare a one-iteration smoke run with a multi-sample baseline or gate CI on fixed wall-clock thresholds.

For CPU or allocation diagnosis, select one case and retain its profile alongside the benchmark samples:

```sh
GOTOOLCHAIN=go1.27.3 go test ./bench/workloads -run '^$' \
  -bench '^BenchmarkWarmSearch/files=128$' -benchtime=3s -count=1 -cpu=4 \
  -cpuprofile=/tmp/gortex-search.cpu.pprof -memprofile=/tmp/gortex-search.mem.pprof
```

Go profiles include setup and validation as well as the timed operation. Interpret stacks accordingly. For startup, cancellation, reconnects and multiple MCP sessions, use the separate isolated transport workload described in `bench/agent-transport/README.md`.
